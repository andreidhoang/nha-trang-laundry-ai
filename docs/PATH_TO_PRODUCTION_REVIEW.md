### 2.2 The environment defect was an evidence-integrity defect, and it is fixed

`CLAUDE.md` described a "known environment defect": a freshly synced `.venv` survives about one
pytest run, after which the editable `.pth` files "stay on disk but stop being applied", producing
"phantom failures (observed: 15 and 28 'failures' where the true count was 0). Not yet root-caused."

It is now root-caused. Three facts compose:

1. This repository sits under `~/Desktop`, managed by the iCloud file provider. Within seconds of
   creation, every file inside the dot-directory `.venv/` receives the BSD `UF_HIDDEN` flag. A plain
   `.txt` probe written into `site-packages` was flagged identically, so this is a directory-level
   behaviour, not a `.pth` or `uv` behaviour — `uv`'s own cache copies stay unflagged.
2. CPython 3.12.11's `site.addpackage` calls `os.lstat` before reading a `.pth` and returns early
   when `st_flags & stat.UF_HIDDEN` is set, emitting only a `-v` trace line
   `Skipping hidden .pth file: ...`. Nothing reaches stderr on a normal run.
3. Every workspace package is an editable whose only route onto `sys.path` is a
   `_editable_impl_*.pth`. When those are skipped the nine packages are simply absent while their
   `dist-info` directories remain — exactly the "on disk but not applied" symptom.

Measured, on this host, on the same commit:

```
.pth flagged hidden, no PYTHONPATH   ->  37 failed, 482 passed
workspace roots on the import path   ->   0 failed, 519 passed
```

All 37 were phantom, and every one was a test that shells out to a subprocess: the parent
interpreter had started while the flag was momentarily clear and the children had not. The decay
time is under ten seconds, so the documented remedy — `rm -rf .venv && uv sync` between suite runs —
could only ever have worked by accident.

**Why this outranks its size.** `AGENTS.md` states that a green test run is not completion evidence.
The inverse was the live risk here: a *red* run that was not a defect. An engineer or agent facing
37 unexplained failures either burns hours chasing them or learns to discount failures — and an
evidence discipline that has learned to discount failures is not an evidence discipline. Every
`checks: PASSED` line in `evidence/delivery-loop/` was produced under this condition.

The fix does not fight the flag. `scripts/workspace_env.py` puts the nine workspace source roots on
`sys.path` and exports `PYTHONPATH` so child processes inherit them; the seven gate entry points and
the root `conftest.py` bootstrap it. The full battery now passes with every `.pth` deliberately
flagged hidden and no ambient `PYTHONPATH`.

One constraint surfaced while doing it, and is worth recording because it is the pinning working
correctly: seven scripts are hash-pinned by recorded evidence. Adding a single import line to
`capture_local_agent_evidence.py`, `verify_agent_runtime.py` and two others invalidated the evidence
they had produced, and `test_local_agent_evidence.py` failed immediately. Those files were reverted
and are deliberately excluded from the bootstrap; nothing under `evidence/` was modified.

### A sequencing defect in the plan

`CONSENT-STOP-001` requires the egress suppression re-check to happen **inside the send
transaction**. The only send transaction in the plan is built by `CHANNEL-ZALO-001` — which depends
on `CONSENT-STOP-001`. The declared graph stays acyclic only because that dependency is not written
down, so the controller will happily offer `CONSENT-STOP-001` for work that cannot be finished.

The resolution is scope, not ordering: `CONSENT-STOP-001` should build the **reusable egress guard
that a sender calls**, plus the whole ingress half, and `CHANNEL-ZALO-001` should be the item that
proves the guard actually runs inside a real send transaction. Written that way both are buildable in
the current order. This needs an owner or engineer decision before the item is started; it was left
`PENDING` rather than started half-open.

### Known test-hygiene debt

`apps/worker/tests/test_agent_pipeline.py` and the other agent-run tests accumulate `PENDING` rows in
the shared test database, because `agent_tool_calls` is append-only and cannot be truncated. The race
test asserts *no double-claim* rather than *exactly one claimant* for that reason, which is the
stronger invariant anyway. It will bite whoever adds an ordering-sensitive test.
