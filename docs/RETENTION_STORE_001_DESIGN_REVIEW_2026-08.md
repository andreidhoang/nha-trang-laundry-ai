# RETENTION-STORE-001 — the design that was refuted, and what it would take

**Produced:** 2026-08-18 · **Status of this document:** analysis. It is **not normative**, resolves no
decision, authorizes no capability, and completes no delivery item. `delivery/` remains machine truth.

`RETENTION-STORE-001` is `BLOCKED` on `DEC-018` and `DEC-020`
(`docs/DECISION_REQUEST_RETENTION_EXECUTION_2026-08.md`). This document exists so that the design work
survives the block. Six investigators mapped every ledger surface, one synthesized a design, and three
adversarial reviewers **all refuted it**. Nothing was implemented.

Whoever picks this item up after the decisions resolve should start from the must-fix lists in §3
rather than from the packet, and should treat §1 as settled facts rather than re-derive them.

## 1. Settled by direct measurement — do not re-derive


Run inside a transaction that was ROLLBACKed; 0 probe tables persisted (verified).

| # | Question | Result |
|---|---|---|
| 1 | Does `UPDATE` on a table with `reject_ledger_mutation` fire? | **Refused** — "ledger tables are append-only" |
| 2 | Can payload be moved with `INSERT..SELECT` into a side table? | **Yes**, 2 of 2 rows moved |
| 3 | **Does `ALTER TABLE ... DROP COLUMN` fire the row trigger?** | **No — DROP COLUMN SUCCEEDS.** DDL does not fire row-level triggers in PostgreSQL 16 |
| 4 | Does `DELETE` from the side table work, leaving the ledger intact? | **Yes** — side 2→1, ledger stayed 2 |
| 5 | **Is the ledger trigger still armed after the DDL?** | **Yes** — `DELETE FROM ledger` still refused |

## What this settles for the design

- The migration does **not** need to drop or recreate any trigger to move a payload column out.
  Question 3 was the main open risk and it is answered empirically, not by reasoning.
- The trigger survives the DDL intact (5), so the ledger guarantee is not weakened by the move.
- FK direction: the side table must reference the ledger (`side.id REFERENCES ledger(id)`), with
  `ON DELETE RESTRICT`. Then deleting a side row cannot touch the ledger, and deleting a ledger row
  is blocked twice — by the FK and by the trigger. `ON DELETE CASCADE` in either direction would be
  a defect; cascade from ledger→side would be a hidden purge path, and side→ledger is impossible.

## The one caveat the probe does NOT cover

`webhook_events` carries `webhook_events_protected`, not `reject_ledger_mutation`. That function
names `encrypted_payload` explicitly in its immutable-column list, so dropping that column leaves a
trigger function referencing a column that no longer exists. PL/pgSQL resolves `NEW.col` at
execution, so it would fail at runtime on the next UPDATE, not at DDL time. **That trigger function
must be re-created (forward-only, in the same migration) without the dropped column.** This is the
one place the design genuinely must touch a trigger, and it is a narrowing, not a relaxation — the
re-created function must still forbid DELETE and still permit only DISPATCH_PENDING → PROCESSED.

## What this means for the item

The packet assumes DEC-008's ten classes map onto tables and that the only obstacle is the ledger
trigger. Measured, the obstacle is smaller in one direction and larger in another: fewer tables need
side tables than the packet implies, and **more tables hold disposable content than DEC-008 has
classes for.** Which class a table belongs to is a business and legal judgement — DEC-008's own
domain — so the uncovered set is a finding for the owner, not something to assign in code.

## 2. The design as proposed

**Classes it would make disposable:** `RAW_WEBHOOK_PAYLOAD`, `ASSISTANT_TRANSCRIPT`

RETENTION-STORE-001 lands as ONE forward-only migration (0028_disposable_payload_stores.sql) plus code changes, and it makes exactly TWO classes disposable: RAW_WEBHOOK_PAYLOAD and ASSISTANT_TRANSCRIPT. Both are PURGE under DEC-008; both are the classes that actually hold customer content today (the webhook ciphertext, and the operator's free-text question, which `redact_text` strips of credentials and phone numbers but NOT of customer names — verified at apps/api/tests/test_assistant_postgres.py:376-386, which asserts the phone is gone and says nothing about "chị Lan").

Two side tables are created: `webhook_event_payloads` (holds the one column `encrypted_payload`) and `assistant_turn_payloads` (holds `question`, `answer`, `links`). Each is keyed 1:1 by the ledger row's primary key, carries a BEFORE UPDATE guard so the payload stays immutable for as long as it exists, and carries NO delete guard — DELETE is the purge. That is the precise sense in which nothing is weakened: immutability is preserved and disposability is added alongside it, rather than traded for it.

FOUR FINDINGS FROM THE INVESTIGATION THAT CHANGE THE SHAPE OF THE WORK, all verified against source:

(1) The packet's trigger table is stale. `webhook_events` does NOT carry `webhook_events_append_only` — migration 0008 line 3 DROPs it and installs `webhook_events_protected` -> `protect_webhook_event()`, which forbids DELETE outright but PERMITS one UPDATE (DISPATCH_PENDING -> PROCESSED) and names `encrypted_payload` by name in its immutable-column list (0008:16). Dropping that column would leave a plpgsql body referencing a field that no longer exists, and plpgsql resolves record fields at execution time, so the next legal status UPDATE would raise `record "new" has no field "encrypted_payload"`. The function must therefore be re-created. The tasking authorizes exactly this ("If a trigger function must be re-created because it names a column that moved, say so explicitly and show the forward-only way to do it"), and the way is CREATE OR REPLACE FUNCTION with a body byte-identical to 0008:5-28 minus that one comparison line. The TRIGGER OBJECT is never dropped, 0008's file and checksum are never touched (migrations.py:74-79 raises if a deployed file changes), and migrations.py:68-88 runs each file inside one `connection.transaction()` — PostgreSQL DDL is transactional — so the immutability clause disappears at the same instant the column it protected ceases to exist. There is no window in which the column exists unguarded and no window in which the legal UPDATE fails.

(2) BLOCKER FOUND AND FIXED IN-ITEM: the assistant answer is stored TWICE. `AssistantService.post_turn` (apps/api/src/nha_trang_laundry_api/assistant.py:436) wraps the write in `IdempotencyRepository.execute`, whose executor returns `_turn_mapping(turn)` (:496-503) carrying `"answer"` and `"links"`. `idempotency.py:88-96` persists that document verbatim into `command_idempotency_records.response` JSONB, and `protect_idempotency_record` (0007:14-31) rejects DELETE outright and rejects any UPDATE once `response IS NOT NULL`. Purging `assistant_turn_payloads` alone would leave a full, permanently undeletable copy of the answer one table over, making a COMPLETED 180d PURGE a lie — precisely the "control that looks satisfied" failure retention.py exists to prevent. So `_turn_mapping` must stop carrying payload, and replay must rehydrate from the side table. The question half is already clean: the idempotency *request* payload does carry the un-redacted question, but idempotency.py:53-63 stores only its JCS-SHA256 `request_hash`, never the text.

(3) AGENT_RUN_PAYLOAD and INCIDENT_EVIDENCE have NO payload to separate, and the current refusal reason for them is factually false. Tool arguments were never persisted — only `request_fingerprint`, a sha256 over the canonical JSON (agent_runs.py:596-604); result bodies exist only as `{result_code, status_code, top_level_keys}`. `customer_incidents` holds identifiers, enums, booleans, a timestamp and two sha256 hashes; the evidence itself is not in this database (spec's `evidence_assets` is 0/6 built, and DEC-009 forbids fetching customer media). Building side tables for these would manufacture a customer-PII store in order to satisfy a control whose purpose is to shrink PII stores, and would let a run report COMPLETED having deleted nothing. Both stay refused, with corrected reasons.

(4) `LEDGER_BACKED_CLASSES` is wrong in two of its six members and its refusal string is now false for four. `customer_incidents` carries `customer_incidents_no_hard_delete` -> `reject_operational_hard_delete()` (DELETE-only; UPDATE is entirely unguarded), not an append-only trigger. And for CONSENT_EVIDENCE and SECURITY_AUDIT_EVENT the string "a schema decision is required" is false — DEC-008 made the decision and the answer was "never". Writing a false reason into an append-only `retention_purge_runs` record and its domain event is the failure mode this module exists to prevent, so the set is replaced by an exhaustive per-class detail map.

RETENTION-001 behaviour is preserved bit for bit: the four guard branches of `run_purge` keep their exact order and outcomes (no schedule -> REFUSED_NO_APPROVED_SCHEDULE, not enabled -> SKIPPED_DISABLED, hold -> REFUSED_LEGAL_HOLD, unsupported -> REFUSED_UNSUPPORTED_STORE), every run still writes a record through `commit_material_change`, and the disposal statement executes as the FIRST statement of the same `mutation(cursor)` closure that inserts the run row — so the deletion, the run record, the domain event, the audit event and the outbox row commit together or not at all. Purge is idempotent because the second run's cutoff matches rows that are already gone and reports `affected_row_count = 0` — honest zero after a statement really ran, categorically different from today's zero, which reports success having issued no statement.

NO TOMBSTONE. Reject the "nullable purged_at + run_id FK on the ledger row" idea: setting it would require an UPDATE that `protect_webhook_event` and `reject_ledger_mutation` both forbid, and it is exactly the tombstone the packet prohibits. The auditor rule is instead: for a ledger row whose timestamp is at or before the `cutoff_at` of a COMPLETED run for that class, the ABSENCE of the side row IS the evidence of disposal under a named, versioned, DEC-008-referenced schedule. `payload_disposed` is computed at read time from the LEFT JOIN and never stored.

DOC/PACKET STALENESS FOR THE ENGINEER TO CORRECT (read-only investigation; nothing was modified): context/tasks/TASK-retention-store-001.md:22-28 names `webhook_events_append_only` (dropped by 0008) and calls INCIDENT_EVIDENCE "ledger-backed / append-only" (it is DELETE-only-guarded); says "Five of the nine section 15 data classes" when there are ten classes and six were in LEDGER_BACKED_CLASSES; says "The remaining four have no backing store at all" when only three do — ORDER_FINANCIAL_RECORD has four delete-protected backing tables. docs/DECISION_REQUEST_RETENTION_2026-08.md:33-38 repeats the same "carrying reject_ledger_mutation" premise for INCIDENT_EVIDENCE, and its Decision B rationale ("on a ledger table the trigger rejects UPDATE as well as DELETE") is false for that class. retention.py's module docstring and the LEDGER_BACKED_CLASSES comment say the same. packages/db/tests/test_retention.py:427 has a docstring claiming `reject_ledger_mutation` guards `webhook_events`; the test is green for the wrong reason (protect_webhook_event also raises psycopg.errors.RaiseException) and would not notice the guard being swapped. specs/SECURITY_RELIABILITY_SPEC_V1.md:646-656 still has nine rows and never names ASSISTANT_TRANSCRIPT, which 0027 made a legal class. Migration 0020 does not reference `webhook_events` at all.

### Migration plan as proposed

```text
FILE: packages/db/migrations/0028_disposable_payload_stores.sql

The whole file executes inside ONE transaction — migrations.py:68-88 wraps each file in `connection.transaction()` and PostgreSQL DDL is transactional — so every statement below, including the DROP COLUMNs and the verification RAISEs, commits as one unit or rolls back entirely. `sha256(bytea)` is a CORE function from PostgreSQL 11 onward; do NOT reach for pgcrypto.

Statements in order.

-- STEP 0. FAIL-CLOSED PRECONDITION: no undeletable second copy of an assistant answer may exist.
-- `command_idempotency_records` is protected by protect_idempotency_record (0007:14-31), which
-- refuses DELETE outright and refuses UPDATE once response IS NOT NULL. If any legacy row carries
-- an answer, ASSISTANT_TRANSCRIPT cannot be honestly purged and this migration must not proceed.
DO $$
BEGIN
    IF EXISTS (
        SELECT 1 FROM command_idempotency_records
        WHERE scope LIKE 'assistant-turn:%' AND response IS NOT NULL AND response ? 'answer'
    ) THEN
        RAISE EXCEPTION
            'RETENTION-STORE-001 precondition failed: command_idempotency_records holds an '
            'immutable copy of an assistant answer; purging assistant_turn_payloads would not '
            'dispose of it. See open_questions.';
    END IF;
END $$;

-- STEP 1. The two disposable payload stores. Plain REFERENCES with no ON DELETE clause: the parent
-- ledger row can never be deleted (webhook_events_protected refuses DELETE outright,
-- assistant_turns_append_only refuses every mutation), so cascade semantics would be dead code
-- that misleads a reader. PRIMARY KEY on the FK gives exactly one payload row per ledger row.
CREATE TABLE webhook_event_payloads (
    webhook_event_id UUID PRIMARY KEY REFERENCES webhook_events(id),
    encrypted_payload BYTEA NOT NULL CHECK (octet_length(encrypted_payload) > 0),
    received_at TIMESTAMPTZ NOT NULL
);

CREATE INDEX webhook_event_payloads_retention_idx ON webhook_event_payloads (received_at);

CREATE TABLE assistant_turn_payloads (
    turn_id UUID PRIMARY KEY REFERENCES assistant_turns(turn_id),
    store_id UUID NOT NULL,
    question TEXT NOT NULL CHECK (char_length(question) <= 4000 AND btrim(question) <> ''),
    answer TEXT NOT NULL,
    links JSONB NOT NULL DEFAULT '[]',
    created_at TIMESTAMPTZ NOT NULL
);

CREATE INDEX assistant_turn_payloads_retention_idx ON assistant_turn_payloads (created_at);
CREATE INDEX assistant_turn_payloads_store_idx ON assistant_turn_payloads (store_id, created_at);

-- The CHECK on `question` is carried across verbatim from 0026:15 so the constraint follows the
-- data rather than being quietly lost. `store_id` and the two timestamps are denormalized copies
-- so the cutoff scan and any future store scoping never join back to the ledger.

-- STEP 2. The side-table guard. This is the protection that 0008:16 and 0026's trigger gave the
-- moved columns, relocated rather than removed: the payload is still immutable for as long as it
-- exists. DELETE is deliberately NOT guarded, because DELETE is the purge.
CREATE FUNCTION reject_disposable_payload_update() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
    RAISE EXCEPTION 'disposable payload rows are immutable; they may only be purged';
END;
$$;

CREATE TRIGGER webhook_event_payloads_immutable
    BEFORE UPDATE ON webhook_event_payloads
    FOR EACH ROW EXECUTE FUNCTION reject_disposable_payload_update();

CREATE TRIGGER assistant_turn_payloads_immutable
    BEFORE UPDATE ON assistant_turn_payloads
    FOR EACH ROW EXECUTE FUNCTION reject_disposable_payload_update();

-- STEP 3. The data move. A SELECT plus an INSERT into a brand-new table: no trigger on
-- webhook_events or assistant_turns fires, so nothing is bypassed and nothing is relaxed.
INSERT INTO webhook_event_payloads (webhook_event_id, encrypted_payload, received_at)
SELECT id, encrypted_payload, received_at FROM webhook_events;

INSERT INTO assistant_turn_payloads (turn_id, store_id, question, answer, links, created_at)
SELECT turn_id, store_id, question, answer, links, created_at FROM assistant_turns;

-- STEP 4. Prove the move lost nothing, by count AND hash, on both sides, BEFORE the source columns
-- are dropped. Because the file is one transaction, a RAISE here rolls the entire migration back.
-- This satisfies the packet's "proven by count and hash before and after" inside the migration
-- rather than as a manual step that could be skipped.
DO $$
DECLARE
    src_count bigint; dst_count bigint; src_hash text; dst_hash text;
BEGIN
    SELECT count(*),
           coalesce(md5(string_agg(
               id::text || ':' || encode(sha256(encrypted_payload), 'hex'), ',' ORDER BY id)), '')
      INTO src_count, src_hash FROM webhook_events;
    SELECT count(*),
           coalesce(md5(string_agg(
               webhook_event_id::text || ':' || encode(sha256(encrypted_payload), 'hex'),
               ',' ORDER BY webhook_event_id)), '')
      INTO dst_count, dst_hash FROM webhook_event_payloads;
    IF src_count <> dst_count OR src_hash <> dst_hash THEN
        RAISE EXCEPTION 'webhook payload move lost data: % / % vs % / %',
            src_count, src_hash, dst_count, dst_hash;
    END IF;

    SELECT count(*),
           coalesce(md5(string_agg(
               turn_id::text || ':'
               || encode(sha256(convert_to(question, 'UTF8')), 'hex') || ':'
               || encode(sha256(convert_to(answer,   'UTF8')), 'hex') || ':'
               || encode(sha256(convert_to(links::text, 'UTF8')), 'hex'),
               ',' ORDER BY turn_id)), '')
      INTO src_count, src_hash FROM assistant_turns;
    SELECT count(*),
           coalesce(md5(string_agg(
               turn_id::text || ':'
               || encode(sha256(convert_to(question, 'UTF8')), 'hex') || ':'
               || encode(sha256(convert_to(answer,   'UTF8')), 'hex') || ':'
               || encode(sha256(convert_to(links::text, 'UTF8')), 'hex'),
               ',' ORDER BY turn_id)), '')
      INTO dst_count, dst_hash FROM assistant_turn_payloads;
    IF src_count <> dst_count OR src_hash <> dst_hash THEN
        RAISE EXCEPTION 'assistant transcript move lost data: % / % vs % / %',
            src_count, src_hash, dst_count, dst_hash;
    END IF;
END $$;

-- STEP 5. RE-CREATE THE TRIGGER FUNCTION. This is required, not optional, and it is not a
-- relaxation. `ALTER TABLE ... DROP COLUMN` is DDL and fires no row-level trigger, so the drop
-- itself is legal. But plpgsql resolves record field references at EXECUTION time against the
-- current tuple descriptor, so a body still naming NEW.encrypted_payload after the column is gone
-- raises `record "new" has no field "encrypted_payload"` on the next UPDATE — bricking the one
-- legal mutation the trigger exists to permit. The choice is not "replace it or not"; it is
-- "replace it, or break the inbound status transition".
--
-- The body below is byte-identical to 0008:5-28 except that the single line
--     OR NEW.encrypted_payload IS DISTINCT FROM OLD.encrypted_payload
-- is removed. The unconditional DELETE refusal, all eleven remaining immutable-column comparisons
-- and the DISPATCH_PENDING -> PROCESSED lifecycle pin are unchanged. The TRIGGER OBJECT
-- `webhook_events_protected` is never dropped, so there is no instant at which the table is
-- unguarded. Migration 0008 is never edited, so its checksum stays locked
-- (migrations.py:74-79 raises if a deployed migration file's content changes).
CREATE OR REPLACE FUNCTION protect_webhook_event() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
    IF TG_OP = 'DELETE' THEN
        RAISE EXCEPTION 'webhook events cannot be hard deleted';
    END IF;
    IF NEW.id IS DISTINCT FROM OLD.id
       OR NEW.provider IS DISTINCT FROM OLD.provider
       OR NEW.channel_account_id IS DISTINCT FROM OLD.channel_account_id
       OR NEW.provider_event_id IS DISTINCT FROM OLD.provider_event_id
       OR NEW.payload_hash IS DISTINCT FROM OLD.payload_hash
       OR NEW.event_type IS DISTINCT FROM OLD.event_type
       OR NEW.contact_binding_id IS DISTINCT FROM OLD.contact_binding_id
       OR NEW.channel IS DISTINCT FROM OLD.channel
       OR NEW.opt_out_disposition IS DISTINCT FROM OLD.opt_out_disposition
       OR NEW.opt_out_registry_version IS DISTINCT FROM OLD.opt_out_registry_version
       OR NEW.received_at IS DISTINCT FROM OLD.received_at
       OR OLD.processing_status <> 'DISPATCH_PENDING'
       OR NEW.processing_status <> 'PROCESSED' THEN
        RAISE EXCEPTION 'webhook event payload and lifecycle are immutable';
    END IF;
    RETURN NEW;
END;
$$;

-- No equivalent step is needed for assistant_turns: `reject_ledger_mutation` (0001:50-55) is a bare
-- RAISE that names no columns, so dropping columns from that table cannot break it.

-- STEP 6. Drop the source columns. The CHECK constraints attached to them
-- (octet_length(encrypted_payload) > 0; char_length(question) <= 4000 AND btrim(question) <> '')
-- drop with them and have already been re-created on the side tables in STEP 1.
ALTER TABLE webhook_events DROP COLUMN encrypted_payload;
ALTER TABLE assistant_turns DROP COLUMN question;
ALTER TABLE assistant_turns DROP COLUMN answer;
ALTER TABLE assistant_turns DROP COLUMN links;

-- Nothing else in the schema references the dropped columns: no view, no index
-- (assistant_turns_store_idx and assistant_turns_staff_idx are on store_id/staff_user_id/
-- created_at/turn_id; webhook_events_dispatch_idx is on processing_status/received_at), and no FK.

-- DELIBERATELY NOT IN THIS MIGRATION:
--  * no `purged_at` / `run_id` column on either ledger row — it would require an UPDATE both
--    guards forbid, and it is the tombstone the packet prohibits;
--  * no change to retention_purge_runs.outcome's CHECK (0023:68-71) — the existing five values
--    cover every path, including the REDACT refusal, so no DROP/ADD CONSTRAINT is needed;
--  * no GRANT/REVOKE/RLS — no migration in 0001-0027 establishes a role layer, and inventing one
--    here is out of scope (see open_questions).

```

A `retention_disposal_records(run_id, subject_table, subject_key, subject_occurred_at)` table under reject_ledger_mutation is one valid shape and stores nothing new — every key it names already lives forever in the ledger row, so it is not a tombstone and retains no payload. **Findings:**

- VERDICT: refuted on narrow grounds. The architecture survives the lens — the trigger re-creation is sound, the FK direction is safe, the derived supported-set is sound. What fails is the design's headline claim that it weakens NOTHING. Two verified defects (an unguarded DELETE path and a legal-hold TOCTOU) mean the design as written removes a database-enforced guarantee and replaces it with code discipline. Salvageable with the must_fix list applied; not scrappable.
- LENS Q1 — does the re-created trigger function permit anything the old one forbade? NO, VERIFIED CLEAN. I compared the proposed body against packages/db/migrations/0008_operations_constraints.sql:5-28 and against the full column list of webhook_events at packages/db/migrations/0007_operations_control.sql:33-51. The table has 13 columns; 0008 names 12 of them as immutable (everything except processing_status, which the lifecycle clause pins). The replacement keeps all 11 remaining comparisons, the unconditional DELETE refusal, and the DISPATCH_PENDING -> PROCESSED pin. Critically, `grep -rn webhook_events packages/db/migrations/` shows the LAST migration to touch that table is 0009 (an FK reference only) — no migration after 0008 adds a column to webhook_events or amends protect_webhook_event. So CREATE-OR-REPLACE-with-the-0008-body-minus-one-line cannot silently revert a later amendment, which was the top refutation candidate. The no-window claim also holds: pg_proc changes are transactional and invisible to concurrent snapshots, migrations.py:68-88 runs the file in one connection.transaction(), and the ALTER TABLE in STEP 6 takes ACCESS EXCLUSIVE, so no concurrent session ever sees the relaxed function while the column still exists.
- LENS Q3 — can a purge of a side table mutate a ledger row indirectly? NO, VERIFIED CLEAN. `grep -rn 'ON DELETE' packages/db/migrations/` returns ZERO matches across 0001-0027, so no CASCADE exists anywhere in the schema to inherit. Both proposed FKs are plain child->parent (webhook_event_payloads.webhook_event_id -> webhook_events.id, assistant_turn_payloads.turn_id -> assistant_turns.turn_id) with no ON DELETE clause; PostgreSQL fires referential action triggers on the PARENT for parent-side DELETE/UPDATE, and a child-row DELETE fires nothing on the parent. The FK is in fact net-strengthening: it makes a hypothetical TRUNCATE of webhook_events fail on a dependent table where before it would have succeeded (TRUNCATE was never covered by the BEFORE UPDATE OR DELETE row trigger).
- LENS Q2 — DOES A SIDE TABLE WITHOUT ITS OWN TRIGGER CREATE A MUTABLE PATH INTO DATA THAT SHOULD BE IMMUTABLE UNTIL ITS SCHEDULE FIRES? YES. THIS IS THE REFUTATION. Today the webhook ciphertext is protected by a DB-enforced absolute: protect_webhook_event (0008:7-9) raises on every DELETE, so the payload cannot be destroyed by any application code path, bug, or operator mistake — the database, not retention.py, is the enforcer. After 0028 as designed, webhook_event_payloads and assistant_turn_payloads carry a BEFORE UPDATE guard and NO delete guard at all, so ANY session on the application connection can run `DELETE FROM webhook_event_payloads WHERE received_at > now() - interval '1 hour'` and destroy today's customer content: no schedule check, no legal-hold check, no cutoff check, no retention_purge_runs row, no domain event, no audit row. The design's own rationale ('DELETE is the purge') is exactly what converts a database guarantee into code discipline, and this repo's whole trigger layer exists on the premise that code discipline is not sufficient (see the 0023 header comment: legal holds exist to prevent 'we deleted it during an investigation'). Worse variant: unguarded DELETE plus unguarded INSERT on the side table means delete-and-reinsert-different-ciphertext is now possible — payload substitution that protect_webhook_event's immutable-column list made structurally impossible. The ledger's payload_hash makes it DETECTABLE after the fact; it no longer PREVENTS it.
- LEGAL-HOLD TOCTOU: the design makes deletion real while leaving the hold check outside the deleting transaction, so a hold can be bypassed. retention.py:362-373 (active_hold_exists) runs on its own cursor at retention.py:409, and the DELETE would run inside commit_material_change's transaction (transactions.py:62-64), reached later via _record_run. Under psycopg3's default autocommit=False an implicit transaction is already open, so `connection.transaction()` degrades to a SAVEPOINT and the hold read keeps its original snapshot; under autocommit=True the two are separate transactions outright. Either way, a legal hold committed by place_legal_hold (retention.py:239-294) between the check statement and the DELETE is not seen, and the purge proceeds and destroys held data irreversibly. Before this item the race was harmless because the COMPLETED branch deleted nothing (retention.py:434-446, affected_row_count hardcoded 0); making the purge real is precisely what turns a benign race into irreversible loss during an investigation — the exact outcome 0023:8-9 says the table exists to prevent.
- PURGE BATCHING CAN HALT EARLY AND REPORT A FALSE HONEST-ZERO. The design's statement shape `DELETE FROM {table} AS t WHERE t.ctid IN (SELECT ctid FROM {table} AS t WHERE ... LIMIT 10000)` is ambiguous about whether `extra_predicate` (the consent-evidence carve-out) sits in the inner LIMIT subquery or only on the outer DELETE. If it is only on the outer clause, an inner batch that fills entirely with consent-held rows deletes zero rows while aged, deletable payloads remain — and the design's own drain rule ('repeat until a run reports 0') then stops, writing a COMPLETED run with affected_row_count 0 that means the opposite of what it appears to mean. That is the 'control that looks satisfied' failure the module's docstring names.
- SUPPORTED_PURGE_CLASSES CANNOT WIDEN BY ACCIDENT, BUT IT IS NOT BOUND TO A REAL, MIGRATED, NON-LEDGER TARGET. Deriving it as frozenset(PURGE_TARGETS) is genuinely good and the import-time partition assertion closes the default/fallback hole. But a single dict entry is still all it takes, and nothing structurally prevents that entry from naming (a) a ledger table — `PurgeTarget(table='assistant_turns', ...)` would issue a DELETE that assistant_turns_append_only (0026:29-31) rejects, aborting commit_material_change and leaving NO run record; or (b) a table the deployed database does not have — code shipped at 0028 against a DB still at 0027 raises UndefinedTable inside the mutation closure, same total rollback, same missing record. Fail-closed on data in both cases, so this is findings-level rather than blocking, but the proposed test suite only asserts the literal two-member set, which a developer adding a third target simply edits.
- BEHAVIOURAL DELTA THE DESIGN CLAIMS DOES NOT EXIST: 'RETENTION-001 behaviour is preserved bit for bit' is false for the failure path. Today every call to run_purge writes a retention_purge_runs row because the mutation only inserts that row (retention.py:459-483). Once the DELETE is the first statement of the same closure, any disposal failure (statement timeout, lock timeout, deadlock, FK/trigger rejection, missing table) rolls the run record back with it, and an attempted purge leaves no trace — contradicting 0023:63-65 ('A purge that left no run record did not happen as far as this system can prove'). It is fail-closed with respect to the DATA, so not a blocker, but it must be either handled (record the failure in a fresh transaction after rollback) or stated as an accepted delta rather than denied.
- THE CUTOFF COLUMN IS NOW RETENTION-LOAD-BEARING AND LIVES OUTSIDE THE LEDGER. webhook_event_payloads.received_at and assistant_turn_payloads.created_at are denormalized copies that alone decide whether a row is disposable. Both are UPDATE-protected once written, but nothing makes them equal to the ledger's authoritative timestamp at INSERT time, so a writer bug (or a future writer) could persist a value that permanently exempts a payload from its schedule — retention evasion with no trigger to catch it. A composite FK (turn_id, created_at) / (id, received_at) against a UNIQUE INDEX on the parent makes divergence structurally impossible, is forward-only, and drops nothing.
- CONFIRMED-IN-DESIGN, NOT A NEW DEFECT: the idempotency shadow copy is real and I verified it independently. apps/api/src/nha_trang_laundry_api/assistant.py:496-503 (_turn_mapping) returns 'answer' and 'links'; idempotency.py:84-96 writes that document verbatim into command_idempotency_records.response; protect_idempotency_record (0007:14-31) refuses DELETE outright and refuses any UPDATE once OLD.response IS NOT NULL. So without the design's fix, an ASSISTANT_TRANSCRIPT purge reporting COMPLETED would leave a permanently undeletable full copy of the answer one table over. The design found this and ships the fix; I confirm both the defect and that the fix (strip payload from _turn_mapping, rehydrate replays from the side table) closes it. The question half is clean as claimed — idempotency.py:53-63 persists only the JCS-SHA256 request_hash.

Cost of the rewrite: ACCESS EXCLUSIVE on the table plus a transient doubling of its disk footprint. Note the old relfilenode's disk blocks are unlinked but not zeroed, which is the ordinary backup-policy residue section 15 already contemplates, not a hidden retention.
- THE DEPLOYED ROLE LAYER EXISTS AND IT BLOCKS THE PURGE; open_question #10 is factually inverted. scripts/apply_demo_grants.py:33-35 executes, for both `laundry_api` and `laundry_worker`: `GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA public`, then `REVOKE DELETE, TRUNCATE, REFERENCES, TRIGGER ON ALL TABLES IN SCHEMA public`. packages/evals/tests/test_demo_stack.py:283-284 pins that exact text. So the design's claim that 'purge discipline is code-only' and 'no migration establishes a role layer... inventing one here is out of scope' is wrong about the system as deployed: DELETE is already revoked from every application identity, and an enabled purge run under either role dies with InsufficientPrivilege.
- CONSEQUENCE OF THE ABOVE THAT DESTROYS EVIDENCE: because the design puts the DELETE as the FIRST statement of the `mutation(cursor)` closure, and `commit_material_change` (transactions.py:62-64) runs `mutate(cursor)` inside `with connection.transaction()`, any raise from the DELETE rolls back the run row, the domain event, the audit event and the outbox row together. RETENTION-001's contract is explicit at retention.py:383 -- 'Always writes a run record, including when it refuses.' After this change, a permission denial, a lock_timeout, a statement_timeout or a serialization failure on the first (largest) purge leaves ZERO retention_purge_runs evidence that a purge was even attempted. Today every path leaves a record; the design silently removes that for the only paths that now touch data.
- SECOND GRANT CONSEQUENCE, A HARD BREAK ON AN ALREADY-PROVISIONED STACK: scripts/generate_demo_material.py:170-175 contains no `ALTER DEFAULT PRIVILEGES` (verified by grep -- only GRANT CONNECT, GRANT USAGE ON SCHEMA, GRANT CREATE to laundry_migrate, and three REVOKE CREATE). `GRANT ... ON ALL TABLES` is a one-shot snapshot. Therefore the two tables 0028 creates, owned by laundry_migrate, carry NO privileges for laundry_api or laundry_worker until apply_demo_grants.py is re-run. After 0028 the writers in inbox.py and assistant.py INSERT into those tables, so on any stack provisioned before this item, every inbound webhook write and every assistant turn write fails with `permission denied` until a human re-runs the grants script. The migration plan does not mention this ordering dependency at all.
- THE ROLLBACK NARRATIVE IS FALSE AS WRITTEN. 'Up to the moment a schedule is enabled, rollback is total and costless' is not true, because the schema change and the code change are coupled in one deploy. Pre-0028 code writes `encrypted_payload` into webhook_events (inbox.py:110-134) and question/answer/links into assistant_turns (assistant.py:104-129); after STEP 6 those columns do not exist, so a code revert breaks every inbound webhook and every assistant turn and can only be recovered by a NEW forward migration. Worse, compose.production.yaml gates api and worker with `depends_on: migrate: condition: service_completed_successfully`, which gates START only -- during a rolling `docker compose up` the OLD api and worker containers stay live while `migrate` runs, so the entire ingress path fails for the length of the migration window and until the new images are up. There is no expand/contract phase.
- THE COUNT-AND-HASH 'PROOF' IS TAUTOLOGICAL AND CAN NEVER FIRE, though the migration is nonetheless lossless -- for a reason the design does not state. Verified: STEP 1's `CREATE TABLE child (pid uuid PRIMARY KEY REFERENCES parent(id), ...)` acquires ShareRowExclusiveLock on the parent (pg_locks showed AccessShareLock + ShareRowExclusiveLock on `parent`, both granted, inside the open transaction). ShareRowExclusive conflicts with RowExclusive, so every concurrent INSERT into webhook_events and assistant_turns blocks from STEP 1 until the migration commits, and STEP 3's READ COMMITTED snapshot therefore sees a frozen source. So no rows can be lost -- but only as an artifact of foreign-key lock internals, not as a stated guarantee, and STEP 4 then compares source and destination inside the same transaction where the only writer is the migration itself. It is a concurrency canary that the FK lock has already made unreachable, presented as 'proven by count and hash'. Related operational hazard: with no lock_timeout, the migration stalls all webhook ingress for the full duration of a whole-table INSERT...SELECT plus a whole-table hash pass.
- THE BATCH LIMIT MAKES `COMPLETED` MEAN 'PARTIALLY DISPOSED', which breaks the design's own auditor rule. PURGE_BATCH_LIMIT = 10_000 with 'drained by repeating until a run reports 0' means a single COMPLETED run routinely leaves rows below its own cutoff_at in place. The stated auditor rule is 'for a ledger row whose timestamp is at or before the cutoff_at of a COMPLETED run for that class, the ABSENCE of the side row IS the evidence of disposal'. The contrapositive an auditor needs -- presence below cutoff after COMPLETED means something is wrong -- is now false by construction, and over-retained data is indistinguishable from a normal batch boundary. The PurgeOutcome vocabulary has no PARTIAL and the run record carries no remaining count.
- STEP 4's `md5(string_agg(...))` can abort a correct migration. string_agg materializes one text datum; at roughly 101 bytes per webhook row it reaches PostgreSQL's 1 GB varlena ceiling near 10.6M rows and fails with `invalid memory alloc request size`, rolling back a migration in which nothing was actually wrong. A commutative aggregate over per-row digests, or a FULL OUTER JOIN comparison, has no such ceiling.
- THE PURGE CUTOFF COLUMN IS CALLER-SUPPLIED (latent, not yet exploitable). inbox.py:74 is `received_at = command.received_at or datetime.now(UTC)`, and `InboundWebhook.received_at` is an optional field on the command. The design denormalizes that value into webhook_event_payloads.received_at and makes it the purge predicate. A backdated envelope would purge its own payload early; a future-dated one would never be purged. Grep shows the only callers passing received_at today are packages/evals/src/nha_trang_laundry_evals/synthetic_consent.py:94,159 -- no production path sets it -- so this is latent, but a retention cutoff must key off a system-assigned ingestion timestamp.
- THE BATCHED DELETE IS UNDERSPECIFIED IN A WAY THAT CHANGES THE ROW COUNT. `DELETE FROM {table} AS t WHERE t.ctid IN (SELECT ctid FROM {table} AS t WHERE ... LIMIT n)` reuses the alias `t` in both scopes and the design never says whether `extra_predicate` (the correlated consent carve-out, which references `t.webhook_event_id`) is placed in the inner subquery, the outer WHERE, or both. Inner-only is correct; outer-only makes the LIMIT select rows the predicate then excludes, so a batch silently under-deletes and the drain loop can never reach zero in one pass.
- MECHANICS THAT DO CHECK OUT, stated so the verdict is not read as a blanket rejection. (a) Interruption is atomic: migrations.py:68-88 wraps the SQL file AND the schema_migrations INSERT in one `connection.transaction()`, so a kill at any point leaves the database at 0027 with no side tables, no dropped columns and no replaced function. (b) psycopg 3.2.3 is safe with the literal `%` in `LIKE 'assistant-turn:%'` and the jsonb `?` operator: `_queries.PostgresQuery.convert` takes the `else: self.query = bquery` branch whenever params is None, skipping placeholder parsing entirely (verified in the installed source). This matters because grep shows NO existing migration contains a `%` character, so 0028 would be the first. (c) Multi-statement files and DO $$ blocks work (0017 is the precedent). (d) `sha256(bytea)` is core since PG 11 and the target is postgres:16.10-alpine. (e) DROP COLUMN fires no row-level trigger and raises no dependency error, because webhook_events_protected (0008:31-33) has no column list and no WHEN clause -- confirmed by the live ALTER TABLE succeeding on a table with an equivalent trigger. (f) 0026's columns are all NOT NULL and its CHECK is carried verbatim, so the backfill cannot violate the new constraints. (g) No CREATE VIEW exists anywhere in migrations 0001-0027; apps/api/tests/test_assistant_postgres.py:126-133 is a per-name existence check, not a count of all tables, so it will not break.
- PIN THAT MUST MOVE, CONFIRMED: packages/db/tests/test_migrations.py:11-37 enumerates every (version, name) pair through ('0027','assistant_transcript_retention') and asserts list equality. It will fail until ('0028','disposable_payload_stores') is appended. The design lists this. 0008's checksum stays locked as long as its file is untouched (migrations.py:74-79), which CREATE OR REPLACE FUNCTION in 0028 satisfies.

## 4. Open questions the design could not answer

These are business and legal judgements, not engineering choices. Three of them became `DEC-018`,
`DEC-019` and `DEC-020`; the rest are recorded here so they are not rediscovered.

- CONSENT / RAW-PAYLOAD CLASS COLLISION. A 'STOP' message's ciphertext is simultaneously RAW_WEBHOOK_PAYLOAD (30d PURGE) and the evidence for a consent withdrawal, because consent_events.evidence_webhook_id (0007:87) points at exactly that webhook row, and DEC-008 retains consent evidence indefinitely. DEC-008 does not say whether payload_hash + opt_out_disposition + opt_out_registry_version suffice to evidence a withdrawal once the raw bytes are gone. The design fails closed and carves those rows OUT of the purge, because deletion is irreversible and retention is not. The owner should confirm the carve-out or authorize its removal; either way it is a signed answer, not an engineering default.

- agent_drafts.draft_text AND agent_draft_reviews.edited_text HAVE NO ASSIGNED RETENTION CLASS. draft_text (0021:29, up to 4000 characters) is the only free text anywhere in the agent-run aggregate, it is customer-facing content the model composed, and it is the only column in that aggregate whose deletion would actually dispose of something (the AGENT_DRAFT_RECORDED event carries only draft_character_count, never the text). AGENT_RUN_PAYLOAD (90d PURGE) and CONVERSATION_BODY (180d REDACT) both plausibly cover an agent-authored outbound message body and they differ in BOTH period and disposition. edited_text is staff-authored and may be a third class again. DEC-008 names neither because migration 0021 postdates both spec §15 and the DEC-008 request document — the identical gap ASSISTANT_TRANSCRIPT got an explicit fix for in migration 0027. This needs a DEC-008 amendment; choosing either way in code would be code deciding policy.

- ORDER_FINANCIAL_RECORD IS A SIGNED PURGE WITH NO SEPARATION DIRECTION. DEC-008 Decision A signs 3650d PURGE against orders / quotes / quote_revisions / order_settlements, every one of which is delete-protected, and DEC-008's ledger_backed_resolution block names six classes and simply omits this one. Nothing is urgent (the horizon is ten years and the earliest row is days old), but it is an unresolved decision hiding inside a RESOLVED registry entry. Do NOT move quote_revisions.snapshot into a side table to make the class work: that snapshot is the hashed pricing evidence the money-integrity chain depends on.

- WHERE DOES INCIDENT EVIDENCE ACTUALLY LIVE? customer_incidents stores contact_scope_hash and evidence_summary_hash and nothing else that could be disposed of; the spec's home for the evidence, evidence_assets (DOMAIN_DATA_API_SPEC_V1.md:614), is 0/6 built, and DEC-009 resolved that customer-supplied media is never fetched. So DEC-008 schedules 365d PURGE for a class this system does not hold. When evidence_assets is built it should be BORN as the disposable side table — keyed by incident_id, no ledger trigger, purgeable on its own timestamp — and INCIDENT_EVIDENCE joins SUPPORTED_PURGE_CLASSES then, with a tested purge, and not before. Someone should confirm evidence is genuinely not being stored anywhere today.

- REMEDY IF A DEPLOYED DATABASE TRIPS MIGRATION 0028's STEP 0. command_idempotency_records rows carrying an assistant answer cannot be deleted or updated — protect_idempotency_record (0007:14-31) forbids both, permanently, and relaxing it is out of the question. On a fresh or scratch database the guard passes and there is nothing to do. On a database that has already served assistant traffic the migration will refuse, and the only lawful remedies are a business decision: accept that pre-0028 turns are not purgeable and register the class anyway (which makes COMPLETED partly untrue for them), or rebuild the store from a point before those rows. This is a retention-honesty decision, not an engineering one.

- IS `links` PART OF THE TRANSCRIPT OR PART OF THE DECISION RECORD? The design moves it to the disposable side table, because an ORDER_LOOKUP link embeds a live order UUID derived from the question's content and because links are part of what was rendered to the person. The counter-argument is that they are a small closed vocabulary of console routes and are machine-generated. No auditor query needs them — intent plus reason_codes fully state what was decided — so moving them costs the auditor nothing, but it changes what a purged turn shows and is worth an explicit confirmation rather than being settled by whichever way the migration happened to be written.

- SHOULD A SUBJECT-SCOPED LEGAL HOLD SUSPEND NARROWER THAN CLASS-WIDE? retention_legal_holds carries subject_contact_binding_id (0023:40) with its own index, but active_hold_exists (retention.py:362-373) filters on class_name ALONE. Once purge is real, a single subject-scoped hold freezes disposal for the entire class indefinitely — the schedule stops for every customer because of one dispute. The alternative, a row-level exclusion in the purge predicate, has a fail-open failure mode and cannot bind to assistant_turns at all (that table has store_id and staff_user_id but no contact_binding_id). This design deliberately keeps the existing class-wide behaviour, which is the conservative direction; narrowing it is a policy call. Related and minor: retention_legal_holds.class_name (0023:40) has no CHECK and no FK, so a hold can be recorded against an arbitrary string that active_hold_exists will never match — a legal hold that silently protects nothing, a fail-open inside a fail-closed module.

- payload_hash IS AN UNSALTED SHA-256 OF THE PLAINTEXT (inbox.py:204-206) and must survive the purge — production reads it on every duplicate arrival (inbox.py:91) and it is the replay defense and the auditor's commitment to the disposed content. For short, low-entropy Vietnamese messages ('DỪNG', 'ok', a phone number) it is dictionary-reversible, so a residual re-identification surface outlives the 30-day purge. It cannot be removed without breaking the durable inbox. Record it as an accepted residual risk or route it to a decision; do not weaken it to satisfy retention.

- NO DATABASE-LEVEL ACCESS RESTRICTION EXISTS. There is not a single GRANT, REVOKE, CREATE ROLE or ROW LEVEL SECURITY statement across migrations 0001-0027. The two side tables will be the first DELETE-able tables holding customer content, and that DELETE is not role-restricted at the database layer — purge discipline is code-only. Spec §9.4 requires access, export and deletion of raw inbox data to be audited AND restricted; commit_material_change supplies the audit, nothing supplies the restriction, and DEC-008 additionally assigns 'access restriction' to the two retained-indefinitely classes. Establishing a role layer is a security-owner decision and is out of scope for this item.

- DEBUG_LOG IS SCHEDULED BUT UNREACHABLE. No migration creates any log table; logging is not persisted to PostgreSQL at all. If debug logs live in files, stdout or a collector, this control plane can never dispose of them and a purge run against DEBUG_LOG will always be a refusal no matter what is built here. That is an out-of-band retention obligation someone must own.
