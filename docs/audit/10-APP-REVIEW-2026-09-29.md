# Whole-app review — 2026-09-29 (after round 8, main at `ebebceb`)

Three read-only reviews (money and order lifecycle; staff console; platform), each finding then
re-read by the lead against the code before it was kept. Alongside: one continuous real-browser film
of the daily walk and all 32 conformance scenarios on a fresh stack (results in the last section).

**Verdict.** The core is sound where it matters most: payments are serialised (`FOR UPDATE` +
`If-Match` + commit-time ledger trigger `0056`), order creation is exactly-once, authorization is
declared as data and fails closed, and the model boundary holds. What the review found are
**edge-of-lifecycle** defects — states reached by combining two features that were each built
correctly alone (storage fee × partial payment × waiver; cancel × remedy; delivery × prepayment) —
plus UI races and an operations layer that nobody is paged by. None is a reason to stop the pilot;
the P0s should be fixed before a real customer pays a storage fee or uses a transfer deposit.

Severity: **P0** wrong money or data exposure · **P1** a real workflow broken or misleading ·
**P2** robustness / maintainability. "Verified" = the lead read the cited lines.

## P2

  unflagged) — snapshot lines at issue (`invoice_requests.py:1450-1518`).
- **M7** A credit spent on an order is not reissued when that order is refunded no-charge.
- **C7** Deploys: `/staff/*` has no `Cache-Control`, SW fetches without `no-cache`, no "có bản mới"
  prompt — mixed old/new code possible.
- **C8** English leaks: 422 field paths and JS crash messages shown outside "Chi tiết kỹ thuật".
- **C9** Four date/time formats for the same moment (SLA board, `dateTime`, promise, "Cập nhật lúc").
- **C10** The kg/quantity input has no accessible name.
- **C11** Approvals badge fetches up to 100 records every minute, even in hidden tabs.
- **P4** Private shop CA without name constraints; key on the serving host.
- **P5** CI runs integration tests as superuser, never as `laundry_api`/`laundry_worker`.
- **P6** Outbox "pending" counts ~56 never-claimable event types and never prunes.
- **P7** Audit timeline filters on `aggregate_id` alone; indexes lead with `aggregate_type`.
- **P8** Operations `ValueError` → 409 with English text; several `limit` params unbounded
  (`main.py:6431`).
- **P9** Export-request idempotency scoped per store, not per staff member (`exports.py:820`).

## What is genuinely strong (evidence read)

- Payments: row lock + `If-Match` + idempotency hashed with the row version + `0056` commit-time
  ledger/settlement agreement. No double-pay or overpay path was found.
- Quote → order is a compare-and-swap; reserved credits spent in the same transaction in id order.
- One business timezone; reports hash it into the query version; per-store/day ticket lock.
- Authorization as data (`GATED`/`SESSION`/`PUBLIC` or `classify` raises); repositories re-check
  store membership; single-use ID tokens (`jti`, migration 0062); MFA per request.
- Mutation + event + audit + outbox in one transaction; no `innerHTML` anywhere in the console;
  API responses never cached by the service worker; model boundary enforced server-side.
